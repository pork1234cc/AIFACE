## 以下为修复前排查记录

日期：2026-09-26。用户现象：朋友电脑解压便携 ZIP 运行 AIFACE.exe，生成后自动显示慢，但手动刷新网页结果马上出现。本轮为排查，不修改生产程序或重新打包；没有取得朋友电脑日志或直接操作其电脑。

## P1 应修：已取得交付图仍被任务详情读取阻塞

位置：`frontend/src/components/orders/generation-panel.tsx` 的 load。

流程先并发读取批次列表和 finals，再使用同一个15秒 AbortSignal 等待批次详情。只有详情也成功，才调用 setDelivery(finals)。因此 finals 已包含新图片时，详情超时仍使本轮图片更新全部丢弃；重复失败使后续刷新间隔增长为8、16、32、60秒。

已直接提取当前组件的真实 load 函数执行隔离模拟：连续5次 finals 都返回完成图片，详情均失败，setDelivery 调用次数为0，实际调度间隔为8000、16000、32000、60000、60000毫秒。没有通过改写生产代码制造结果。

建议交付结果与任务详情独立更新及处理错误；详情失败不能撤销已成功读取的图片。分别设置请求时限，并保留未结束任务和提交结果不明的写操作保护。

## P1 应修：交付接口跨时点读取，完成时可能返回矛盾状态

位置：`backend/app/services/deliveries.py:finals_data`，以及前端根据 finals.has_open_tasks 决定轮询间隔的分支。

finals_data 分别读取图片版本、交付记录和活动任务，当前 SQLite 读取没有固定同一个事务快照。Worker 恰好在版本查询后提交图片时，能够返回 items有1张、versions为空、has_open_tasks=false 的组合。前端用 versions 判断是否有图，用 has_open_tasks 判断是否快轮询，因而显示无图并进入30秒空闲轮询。

隔离数据库中已在上述读取间隙执行真实 Worker 落盘，稳定复现这一响应。手动刷新再次读取完整数据就会出现图片，与用户现象吻合。建议保证接口读取一致性，并让前端对“交付引用存在但版本缺失”等过渡态保持短间隔重查。

## P2 建议：网络查询失败的等待时间及原因不可见

Worker 连续查询失败后的间隔为10、20、40、80、160、300秒，最长5分钟。后台会继续保留任务，但页面只对 failed/submission_unknown 等状态显示处理信息；queued/running 上的 query_failed 错误及 next_poll_at 没有展示。弱网机器上容易被理解为页面卡住。

已模拟6次查询故障，确认恢复网络后仍要等待原 next_poll_at。退避本身是既有保护策略，应保留合理限速，并显示查询异常、下次检查时间及适当的只读重查入口。由于用户手动刷新即可看到结果，这一项不是该现象的首要解释。
